# allod change

Isolate a change on its own branch, record and push it, open a PR, and reclaim the tree afterward — the whole lifecycle instead of manual git and Forge steps.

```
allod change begin [-d <description> | --resume <description>] [<repo-path>]
allod change list [<repo-path>]
allod change record -m <message> [--files <file>...]
allod change record -M <file|-> [--files <file>...]
allod change submit -t <title> (-b <body> | -F <file|->) [--base <branch>] [--depends-on <text>] [--dry-run]
allod change cleanup <path>
```

## Clones, not linked worktrees

`begin -d` makes a self-contained local clone under `~/changes` instead of a linked worktree. `git clone --no-hardlinks --no-checkout <repo> <path>` is a local clone copying objects over the optimized local transport, never hardlinking them: a hardlink shares the parent's own inode, and the clone's owner — the worker — can `chmod` or overwrite through it, straight through "the parent is untouched". Never an alternates clone either (`objects/info/alternates`), because a `git gc` in the parent can prune what an alternates clone still references. The clone's `origin` is then repointed at the parent's own `origin` URL (a local clone's default origin is the parent's path, not the forge), fetched and pruned, and `origin/HEAD` is re-resolved against the real remote: the local clone step copies whichever branch the parent happened to have checked out, not necessarily the remote's actual default. `agent/<description>` is cut from `origin/<start>` (`--resume` from `origin/agent/<description>` instead, with upstream tracking), and the clone's own `.git/allod-change-branch` records that handoff the same way a linked worktree's did.

Because objects are copied rather than hardlinked or shared through an alternates file, and the branch lives only inside the clone's own `.git`, a sandboxed worker given nothing but its own clone directory can commit freely without ever writing to the parent; nothing in the parent changes until `record` pushes.

A real repository's own `git gc` (or a fetch with commit-graph writing on) writes `.git/objects/info/commit-graph`, which the clone step above copies straight in — not the worker's doing, so `begin` deletes it (and any `.git/objects/info/commit-graphs/` chain) from the fresh clone right after cloning, rather than let the config-safety gate below refuse a brand-new, legitimate clone over a graph the parent itself wrote before `begin` ever ran.

A worktree `begin -d` made before this change keeps working in `list`, `record`, and `cleanup` until it drains; `begin` makes no new ones.

## The ledger

The parent repository records every clone it issues under its own `.git`, where a sandboxed worker cannot reach it: `.git/allod-changes/<description>`, one file per clone, two lines — the clone's absolute path, then its branch (always `agent/<description>`). The file is keyed by the description, never by the clone directory's basename, and `begin -d` creates it with an `O_EXCL` open as the one atomic step in the whole command: two concurrent `begin -d` calls for the same description both pass the advisory "already claimed" check first, but only one of them can win that create, so the loser refuses instead of both ever writing an entry for the same branch. A failure at any later step — the clone itself, the checkout of the new branch, the handoff-file write — removes both the claim and the half-made clone directory.

Only `begin` writes an entry; only `cleanup` removes one. `list`, `record`, `submit`, and `cleanup` resolve a clone back to its parent by scanning the ledgers of every repository under `$WORK_DIR` the way `list`'s no-argument form already walks the workspace — never through the clone's own `.git/config`, which a worker can edit freely. This is also why `begin -d` and `--resume` refuse a repository that is not under `$WORK_DIR`: a clone issued from anywhere else would get a ledger entry none of these commands could ever find again.

That resolution is a path match, nothing more: the candidate path (an explicit one, or the working directory, walked upward until something matches) is resolved to its physical, absolute form and compared against every ledger entry's own physical path, in pure Go. No git command runs against the candidate to decide this — not even `git rev-parse --show-toplevel` — so a hostile clone never gets the chance to run anything before the config-safety gate below has had a say. Only once that match (and the gate) both pass does `list`, `record`, `submit`, `cleanup`, or `run` run its first git command against the clone.

A clone resolved this way is judged by its parent's `protected-branches` entry, so it is never flagged as a misplaced checkout of itself (exit 8); `record`'s "refuse to sweep a shared checkout" guard also does not fire for it, the same as it never fires for a linked worktree, because a clone belongs to one agent alone.

For a ledgered clone, the ledger entry's own branch is the only one `record`, `submit`, and `cleanup` ever trust, never anything inside the clone itself: a worker can switch branches and rewrite the clone-owned handoff file to match, but not the parent's ledger entry. A mismatch refuses with exit code 3, the same family as the moved-checkout refusal a legacy worktree still gets from its handoff file, and `submit` checks it before the branch is ever read for the PR. `cleanup` applies this before it judges or discards anything, so a worker cannot check out a different, clean, already-pushed branch over the ledgered one and have cleanup discard the ledgered branch's own unpushed commits. `record` and `cleanup` also judge "unpushed" for a clone by asking the real remote directly — `git -C <clone> ls-remote --exit-code origin refs/heads/<ledger branch>`, then ancestry against that head, or patch equivalence against the default branch's head when the branch is absent (below) — never against a local remote-tracking ref or the clone's own configured upstream (`branch.<b>.remote`/`.merge`), both a worker's to rewrite without ever pushing anything: a fabricated or stale `refs/remotes/origin/*` ref could otherwise claim a branch already landed, and `remote = .` with `merge` pointing at the branch itself makes git compare the branch against itself and hide every commit. See "Why a worker's clone is safe to sandbox" below for the full contract.

`submit` resolves an unset `--base` against the parent's own default branch, never the clone's: a clone's own `refs/remotes/origin/HEAD` is a worker's to rewrite (`git remote set-head`), so for a ledgered clone the base is always asked of the repo that issued it.

Before pushing, or before deleting a clone, `record`, `submit`, and `cleanup` refuse, with exit code 9, a clone whose origin no longer matches the repo that issued it. Both the fetch and the push URL are read with `--all` (`get-url --push` without it shows only the first configured push URL, while `git push` pushes to every one) and must each be exactly one URL, equal to the parent's own fetch URL — a worker can edit its own clone's `.git/config` freely, so this is what keeps it from redirecting a push, adding a second push URL the parent never had, or having `cleanup` delete the only copy of a branch pushed somewhere `cleanup` never looked.

## The config-safety gate

The contract: the overseer never runs git against a clone that could run a command or hide its own state from this gate. A worker owns the clone and can point `credential.helper`, `core.hooksPath`, `core.fsmonitor`, `core.sshCommand`, `core.gitProxy`, `core.editor`, `diff.external`, a filter's clean or smudge command, a merge driver, `gpg.program`, `include.path`, or `includeIf.*` at a command of its choosing; that command runs the moment the overseer — outside the sandbox, running real git — next touches the clone from `list`, `record`, `submit`, `cleanup`, or `run`.

Host-side Git commands on a ledgered clone use isolated Git configuration: no
global or system hooks, filters, credential helpers, or caller-supplied `GIT_*`
settings. The overseer identity is copied into that invocation. This keeps a
worker's attributes and scripts from selecting host-user code. HTTPS remotes
that rely on a global credential helper require a different approved transport.

Each of those refuses, with exit code 11, before its first git command against a clone, for any of:

- `.git` missing, not an ordinary directory, or with no `config` file to read. A worker can swap `.git` for a gitfile pointing at a directory it fully controls; git loads that directory's config just the same, but this gate never reads it unless `.git` is an ordinary directory.
- A `.git/commondir` or `.git/gitdir` file. That is how a linked worktree's own `.git` redirects git to load config, refs, and hooks from another directory entirely — one this gate never reads, so it refuses outright rather than trust where that redirect leads.
- A populated submodule, or a bare `.git/modules` directory. `git status` in the parent descends into a populated submodule and loads its own config, which this gate never reads — sandboxed clones do not support them, populated or not; `begin` itself only ever leaves one unpopulated. Checked last, once every check below has already passed: `hasPopulatedSubmodule` runs `git ls-files` inside the clone, a real git invocation that loads the clone's own `.git/config` in full — unlike the `--file`-scoped read just below, which only ever parses that one file — so it must never run against a clone whose config has not yet been vetted.
- A `.git/config` key outside a fixed allowlist: the `core.*` keys and `remote.origin.url`/`.pushurl` an ordinary clone carries (`.pushurl` is also where the origin rule compares the push URL), plus `branch.<ledger branch>.remote` and `.merge` — but only for the ledger's own branch, and only pinned to `remote = origin` and `merge = refs/heads/<ledger branch>`, the one shape `begin` itself sets. Every other `branch.*` key, for that branch or any other, is refused outright; there is no `.rebase` exception. `extensions.refstorage` and `extensions.objectformat` are also allowed — git itself writes them for a reftable or sha256 repository, and `begin`'s own clone can be either — but `extensions.worktreeconfig` and any other `extensions.*` key stay refused. `remote.origin.fetch` and `core.bare` are pinned the same way, to the one value an ordinary clone has (`+refs/heads/*:refs/remotes/origin/*` and `false`, respectively), rather than accepted with any value at all.
- An executable file under `.git/hooks` not named `*.sample`.
- An unreadable hooks directory, a worker-supplied commit graph, or a symlink anywhere under `.git` (not only in `.git/logs`): git writes many files there — `FETCH_HEAD`, `ORIG_HEAD`, `COMMIT_EDITMSG`, `packed-refs`, reflogs, and more — without taking a lockfile first, so a symlink in place of any of them lets an outside command's write go through it to wherever a worker chose. The walk covers `.git/objects` too, not only the handful of named files elsewhere in this gate.
- A `.git/config.worktree` — a second place to carry a key the allowlist never sees.
- A `.git/info/grafts` file, a `.git/shallow` file, or any ref under `refs/replace/` (`git for-each-ref refs/replace`, with the clone's own ledger lock already held). All three rewrite a commit's own parentage as git reports it, the same class of problem `GIT_NO_REPLACE_OBJECTS` closes for `refs/replace/*` specifically everywhere else this process asks git something — but a replace ref's mere existence is refused here outright, whatever it currently points to, rather than merely asked to behave: `merge-base --is-ancestor`, which `unpushedCommitsForClone` relies on to judge a branch pushed, walks whichever parents git reports, not the real ones recorded in a commit object, so any of the three could otherwise make an unpushed `HEAD` look descended from a remote head it never actually was.
- A tracked hook. `git-hooks/protected-refs-policy`, the global hook dispatcher every runner's own hooks under `~/.config/git/hooks` point at, also runs `$repo/.hooks/<hook>` — or the directory `$repo/.hookspath` names — straight from the clone's own working tree, before the clone's own `.git/hooks`, and it runs any file there by hook name, whatever its own git mode or on-disk executable bit, so both are checked, not just the file's bytes. The gate refuses unless: `.hookspath` is absent from the clone or byte-identical to the parent's own working-tree `.hookspath`; every file under the tracked hooks directory that precedence settles on is byte-identical to the parent's own `origin/<default branch>` blob at that path (read with `git show`, run in the parent, trusted, never the clone); that same file's git mode, in both the clone's own index (`git ls-files --stage`) and its working-tree executable bit, matches the parent's `origin/<default branch>` tree entry for it (`git -C <parent> ls-tree origin/<default>`) — a worker's own `chmod +x` or `git update-index --chmod=+x` on an otherwise byte-identical, non-executable tracked file is refused the same as a byte change, since the dispatcher only cares whether the file runs; that directory holds no file the base does not; and no untracked or ignored file exists under it. **The contract this makes literally true: a change to a tracked hook never comes from a sandboxed worker. The overseer makes it in the parent's own change flow**, the same as any other change to the repository, and this gate only ever confirms a clone's copy still matches what the overseer already committed there.

The config is read with `git config --file <path> --list`, which only reads the file and never executes anything, so the check itself adds no new way to run something. A non-zero exit from that read — a corrupt or unparseable `.git/config` — is itself unsafe, never treated as an empty, trivially safe file: an unreadable config is read as "cannot be vetted", not as "has nothing to vet".

Every outside command (`list`, `record`, `submit`, `cleanup`, `run`) runs git with `GIT_NO_REPLACE_OBJECTS=1` set, and the one place this gate shells out to `git show` directly also passes `--no-replace-objects`: a worker's own `refs/replace/<sha>` entry inside the clone can otherwise substitute a different object's content wherever that `<sha>` is looked up during traversal — including the parent commit a `merge-base --is-ancestor` walk reads next — which would let a worker fabricate history that graphs as already pushed, or hide a tracked-hooks change, without ever running a command itself.

`list` never dies on a clone that fails this gate: its row is printed with state `unsafe` (see below) and no git command is run against it, and listing continues to the next clone. `record`, `submit`, `cleanup`, and `run` still refuse outright (exit 11), since each of those is about to act on the one clone named.

`record`, `submit`, `cleanup`, and `list` also take an exclusive, non-blocking `flock` on the clone's own ledger file — the same two-line file under the parent's `.git/allod-changes` that names the clone and its branch — before their first git command against it (`list`'s own row holds it through every one of its own git commands too, `cloneConfigUnsafeReason`'s, `cloneOriginMismatchReason`'s, the branch check's, and `cloneState`'s `git status`/`git ls-remote` alike, one row at a time, never only probed and released up front), and hold it until they are done; `run` takes that same exclusive lock first too, for its own pre-flight (the config gate, the tracked-hooks check, the branch check — every git command `run` runs before the sandboxed command itself starts), then converts it to shared, atomically (a second `flock` call on the same descriptor, which converts the held lock's own type rather than release and reacquire it), for the whole life of the sandboxed command, one clone at a time as each clone's own pre-flight passes. Two concurrent `run`s over the same clone therefore serialize their pre-flight instead of racing each other's git commands, and a command that cannot get the lock it needs refuses with exit code 13, naming the clone, rather than wait: this is what actually closes the window where a still-running worker's `run` and an outside command could both act on the same clone's config at once — a single file-level lock that either succeeds or does not, with no scope name, systemd unit, or session bus to list or parse back apart, and no race between asking "is anything running" and finding out for sure.

`run`'s own copy of the lock does not live only as long as the `allod` process does: a `flock` is held by an open file description, not by whoever opened it, so `run` duplicates the lock's own file descriptor into the `systemd-run` child it execs (Go's `ExtraFiles`), and `buildBwrapArgs` tells bwrap, with `--sync-fd`, to carry that same fd into the sandboxed process itself rather than close it as an fd bwrap does not otherwise recognize (its own `--die-with-parent` monitoring takes over exactly those low fd numbers otherwise). Even if `allod` is killed outright, the sandboxed command's own copy keeps the lock held for as long as it runs. bwrap itself only honors one `--sync-fd`, so a multi-clone `run` only carries the first-named clone's lock fd this fully; every clone's lock is still duplicated into `systemd-run`, just not guaranteed to survive bwrap's own setup for clones named after the first. `systemctl --user` can still be used by hand to see or kill a `run`'s own cgroup scope (see "The scope" in `docs/allod-change-run.md`), but no outside command's own refusal depends on asking it anything.

## list

One tab-separated row per ledgered clone, plus one per remaining linked worktree from before this change — repo, path, branch, state. The state is the one thing standing between that entry and `cleanup` succeeding: `missing`, `prunable`, `locked`, `detached`, `submodule`, `dirty`, `unpushed`, `unknown`, `unsafe`, `running`, `moved`, or `clean`. `missing` and `prunable` both mean the directory is gone, but differ in what is left to do about it: a clone's ledger entry has no admin side-channel, so `cleanup` on a `missing` path drops the ledger entry itself and says so, nothing left to clear by hand first; a worktree's admin entry is exactly what `git worktree prune` clears instead. `locked` and `prunable` are exclusive to a linked worktree, since a standalone clone has no `git worktree`-level admin entry to go either way. `submodule` is exclusive to a linked worktree too, now: for a clone, the config-safety gate refuses a populated submodule outright (exit 11, before `list` ever computes a per-row state for it), surfacing as `unsafe` (below) rather than `submodule`.

`unsafe` means the clone fails the config-safety gate above, or — checked the same non-dying way, before any git command runs against the clone — its own fetch or push URL for `origin` no longer matches the parent's: `list` never says `clean` for a clone `cleanup` would actually refuse (exit 9) over its origin, the same as it never says `clean` for one the config gate would refuse. Unlike every other command that touches a clone, `list` does not stop at either check: it prints the row with state `unsafe`, runs no git command against that clone, and moves on to the next one, so one hostile clone in a ledger never hides the state of every other clone `list` would otherwise report.

`running` means the clone's ledger file is currently flocked exclusively by something else — almost always a `run` still sandboxing a command inside it — so `list` takes no shared lock of its own and runs no git command against the clone at all, the same "do not touch it" rule `record`, `submit`, and `cleanup` all follow. `moved` means the clone itself is not checked out on the ledger's own branch — a worker switched branches inside the clone — checked, lock permitting, before the git commands `cleanup`'s own state computation runs. Both exist so `clean` keeps meaning exactly "`cleanup` would succeed here right now": a clone `list` cannot safely inspect, or one no longer sitting on the branch `cleanup` would discard or push, is never reported as `clean`.

`cleanup` treats a clone as `missing` only when checking its path reports exactly that — `os.IsNotExist`, nothing seen there at all. Any other error (permission denied; a component of the path turning out to be a plain file, not a directory; anything else `os.Stat` can return) refuses with that error's own text, rather than assume the clone is gone and drop its ledger entry on a guess that could be wrong. So does a path that exists and stats cleanly but is itself a plain file, not a directory: that is "something else is there", never "missing", even though the stat itself raised no error at all.

A clone's own `refs/remotes/origin/*` and `branch.<b>.remote`/`.merge` are both a worker's to rewrite — a worker can create or move a local remote-tracking ref without ever pushing anything, making a stale or fabricated ref look like the branch already landed, or make `@{u}` the branch itself and hide every commit from a naive comparison — so neither is ever consulted for "unpushed". `cleanup` (and `list`, and `record`) ask the real remote directly instead: `git -C <clone> ls-remote --exit-code origin refs/heads/<ledger branch>` gives the branch's actual head there, and the branch counts as pushed only once `git merge-base --is-ancestor HEAD <remote sha>` holds; a branch absent on origin — nothing ever pushed under that name, or the forge deleting it after a rebase-merge — is judged against the default branch's head by patch equivalence instead (no merge commit outside it, then `git cherry`), so work the forge re-landed under new hashes, by rebase-merge or a patch relay onto the default branch, reads as landed rather than unpushed. `cleanup` fetches `--prune origin` before this judgment, because the comparison needs the remote's objects locally and a rebase-merge plus branch deletion is exactly what an unfetched clone has never seen; a failed fetch is a refusal. Any git failure along the way — the fetch, `ls-remote`, the comparison, or `cleanup`'s own `git status --porcelain` dirty check — is a refusal naming the failure, never read as clean or pushed. `list`'s own clone-state computation fails the same way: a `git status --porcelain` it cannot read reports `unknown`, never `clean`. The tracked-hooks check's own `git status --porcelain --ignored` (for the untracked/ignored check over the tracked hooks directory) is held to the same rule, inside the config-safety gate below: unreadable refuses, rather than skip that one check and let the rest of the gate's verdict stand on its own.

## Why a worker's clone is safe to sandbox

The clone's branch lives only inside its own `.git`; the only write `begin` ever makes to the parent is the ledger entry it claims, atomically, before cloning. So a failure at any later step — the clone itself, the checkout of the new branch, the handoff-file write — undoes that claim along with `rm -rf` on the half-made clone, and there is no branch left behind in the parent to clean up, unlike the linked-worktree model this replaces.
